## Goal

If a recent `started` result exists for the same XPI file and tested Zotero release, the daily build reuses it and does not start the plugin again.

## Scope

**In:** Publish each read XPI's SHA-256 as `upstream.xpiSha256`. Add a carry step to the build job of `build.yml`. The step reads the deployed data and writes the reused results into the start plan as `carried` lists. `pnpm start-tests` skips carried pairs. `pnpm add-start-results` merges carried results with the jobs' results. Each entry gets a re-test day once every 7 days, and a failure is tested again on the next run. Update the docs, the schema text, the CHANGELOG, and DESIGN.md, and add a D-entry on the carry's trust and forgery cost.

**Out:** A date on each start result. The user declined it at the question set, so no row holds it. The live check that a run after the merge carries results. The first run after the merge deploys the hashes and carries nothing, so only the second scheduled run can show it. That check is a post-merge read of the run log and needs no row. Showing the SHA-256 on the site stays out, as "Publish each XPI's SHA-256 too" asks only for the data.

## Acceptance criteria

- [x] AC1: `pnpm build` writes `upstream.xpiSha256` on each record that has `upstream` and a start plan item. The value equals that item's `sha256`. `schemas/plugins.v1.schema.json` defines the field as an optional string of 64 lowercase hexadecimal characters. A test in `test/build.test.ts` shows the field equal to the plan item's `sha256`. Schema tests show that the schema refuses an upper-case value, a 63-character value, a 65-character value, and a 64-character value with a `g`. They also show that it accepts one valid value and a record without the field.
- [x] AC2: A carry step of the build job in `.github/workflows/build.yml` runs after `pnpm build` and before the `start-plan` upload. It reads the deployed data at `https://jmgirard.github.io/zotero-plugin-index/v1/plugins.json`. It writes a non-empty `carried` list only into plan items with at least one match outside their re-test day. Other items get no `carried` field. A match is a `started` item of the earlier record's `startTests`. The earlier record must have the item's entry id. Its `upstream` must have the item's `id` and `version`, and an `xpiSha256` equal to the item's `sha256`. The re-test day is the day where floor(t / 86,400,000) mod 7 equals `retestDay(entry)`. Here t is `generatedAt` of the data file that `pnpm build` wrote, in milliseconds. `retestDay` is a pure function from the entry id to a number from 0 to 6. The job keeps `cache-mode: none` and its permissions. `test/workflows.test.ts` checks the step's command and its place.
- [x] AC3: Tests over fixture data show a carried result for a match. They show no carried result for each of these changes alone: a different hash, version, or plugin id, no earlier record for the entry, an earlier record with `failure` and no `upstream`, an earlier record with no `startTests`, an earlier record with no `xpiSha256`, and the re-test day. A record that mixes `started` and other results across versions carries only its `started` items. For one entry over 7 consecutive days, the carry is withheld on exactly one day.
- [x] AC4: On any error, the carry step leaves the plan as `pnpm build` wrote it, prints one line that names the cause, and exits 0. It writes the plan through a temporary file and a rename. The errors include a failed fetch, an answer other than 200, and more than 16 MiB of decoded body, counted as it streams. They also include a body that does not parse as JSON or has no `plugins` list, a read past the time limit, and an unreadable plan or data file. The time limit is a parameter, 60 s by default. A malformed earlier record carries nothing and does not stop the step. Tests plant each listed cause and show the plan file unchanged and the exit status 0.
- [x] AC5: `pnpm start-tests` does not download or start a plan item whose `carried` list names the binary's Zotero version. It counts such an item as carried in its summary line, never as not started, whatever the time. A test with a stub start-test command and a fixture fetch shows a carried item with no request and no start. It also shows that an item whose `carried` list names only another version is downloaded and started.
- [x] AC6: `pnpm add-start-results` adds the carried results of each plan item to its record, beside the jobs' results. A carried result must be `started` and name a Zotero version in `--tested` and in the item's manifest range. A job result for an entry and Zotero version that the plan carries drops with the reason `carried`. `parsePlan` refuses a `carried` that is not an array, an item without a string `zotero`, an item whose `result` is not `started`, and two items with the same `zotero`. Tests show each of these rules and each refused shape. A chained fixture test runs the carry step, `pnpm start-tests`, and `pnpm add-start-results` in turn. It shows that the merged data, read by a second carry, carries the same results again.
- [x] AC7: Some texts state the start rule: README (the `upstream` fields, the `startTests` paragraph, and "Starting plugins in Zotero"), the About page's start-test section, the home page intro and legend, the `startTests` description in `schemas/plugins.v1.schema.json`, and DESIGN.md. The start rule has four parts. A start runs for an XPI file whose SHA-256 differs from the last one tested. It runs for a tested Zotero release with no earlier result. It runs after a result other than `started`. It runs on the entry's re-test day, once every 7 days, in a build that deploys. Each line that `grep -rniE 'daily|each day|every day' README.md site/src schemas cairn/DESIGN.md` lists and that describes start timing agrees with the start rule. README and the CHANGELOG entry name `upstream.xpiSha256` and tell users to fetch `plugins.v1.schema.json` again. `npx -y pnpm@12.15.0 test` and `npx -y pnpm@12.15.0 check` pass.
