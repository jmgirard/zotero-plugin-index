# M040: Answer issues that no bot run answered

- **Status:** review

- **Branch/PR:** m040-sweep-unanswered-issues

## Goal

A daily run answers each open "Add a plugin" or report issue that no bot run answered, such as one whose run was canceled in the `discover` concurrency group.

## Scope

**In:** a new `unansweredIssues` function and `pnpm unanswered-issues` command (`src/issues/`) that list the open issues of one label that no `github-actions[bot]` comment answers. A sweep mode of `pnpm report-issue`, run by `report-issue.yml` on a daily schedule and on dispatch. A `pick` job in `add-plugin-issue.yml` that, on a daily schedule and on dispatch, names up to 3 such issues, and on `issues: opened` names the event's issue; the read and write jobs run `pnpm discover-issue` and `pnpm propose` once for each named issue. `pnpm discover-issue` reads the issue body from the API by `ISSUE_NUMBER` in place of `ISSUE_BODY`. `answerReport` posts no second comment. `issueAnswer` gives the new-pull-request answer when the open bot pull request for the repo closes this issue. Tests, README, CHANGELOG, DESIGN.

**Out:** an issue run that cancels a pending `Discover plugins` run → the candidate row "Answer issues whose run was canceled", narrowed at review. An automatic retry of a failed close of a report issue that the bot already commented on, and a label added to an issue more than 7 days after it opened → the candidate row "Answer report issues left open", narrowed at review. A cap on report issues per person → the row "Limit floods of report issues". An issue that has any bot comment, such as "The bot could not finish", stays for a maintainer, as now. A rerun of the add-plugin write job answers each issue of its batch again, as a rerun of one issue's write job does now; skipping the issues a first attempt answered is not planned, since the issue whose push failed also has a bot comment.

## Acceptance criteria

- [ ] AC1: `unansweredIssues` in `src/issues/unanswered.ts` returns the numbers, oldest first and at most `limit`, of the index repo's open issues (pull requests left out) that carry the given label, were created at least 1 hour and at most 7 days before the given `now`, and have no comment, on any page of the comments, whose author login is `github-actions[bot]`. It returns no numbers when any run on the first page (the 100 newest) of the given workflow file's `issues`-event runs has a status other than `completed`, and it throws when a read fails. Verified by: tests in `test/unanswered.test.ts` with a fixture issue on each side of each condition (label, open state, pull request, both age bounds, a bot comment against another account's comment, a bot comment on the second page of comments, the limit), a `queued` run and an `in_progress` run, and a failed read, each asserting which numbers return or which failure throws.
- [ ] AC2: When the issue already has a comment by `github-actions[bot]`, `answerReport` in `src/reports/issue.ts` posts no comment and sends the close it would send otherwise (completed for a taken report, not planned for a refused one). A failed read of the comments sends nothing and returns status 1. An issue with no bot comment still gets one comment and one close. Verified by: tests in `test/report.test.ts` for the three cases.
- [ ] AC3: `pnpm report-issue --sweep` answers, with `answerReport` and in turn, each issue that `unansweredIssues` returns for the label `report`, the workflow file `report-issue.yml`, and a limit of 20. It exits 1 when the list read fails or any answer has status 1, after it tries the rest. `report-issue.yml` runs it daily on `schedule` and on `workflow_dispatch` from the default branch only, with all sweep runs in one concurrency group that cancels no run in progress, and runs `pnpm report-issue` as now on `issues: opened` with the label `report`, in no group that another run shares. Verified by: tests of a sweep over two unanswered issues and one answered issue (two comments, two closes) and of a sweep whose first answer fails (the second is answered, exit 1); `test/workflows.test.ts` for the triggers, the condition, and the groups.
- [ ] AC4: `add-plugin-issue.yml` runs daily on `schedule` and on `workflow_dispatch` from the default branch only, in the `discover` concurrency group. Its `pick` job, which reads no plugin repo, outputs the issue numbers: on `issues: opened`, the event's issue when it carries `add-plugin` and no number otherwise; on `schedule` and `workflow_dispatch`, those that `pnpm unanswered-issues` prints for the label `add-plugin`, the workflow file `add-plugin-issue.yml`, and a limit of 3. The read job runs `pnpm discover-issue` and the write job runs `pnpm propose`, once for each number, with that number in `ISSUE_NUMBER` and taken only from the `pick` job's output, and each job fails when any of its runs fails, after it tries the rest. `pnpm discover-issue` reads the issue body from the GitHub API for `ISSUE_NUMBER` and no longer reads `ISSUE_BODY`; a failed issue read is the `failed` outcome, so `pnpm propose` comments that the bot could not finish and leaves the issue open. Verified by: `test/workflows.test.ts` for the triggers, the condition, the group, the `pick` outputs, and the loops; tests of a body read from a fixture API and of the `failed` outcome for HTTP 503 and HTTP 404 answers.
- [ ] AC5: When the bot pull request open for the issue's repo has exactly one `Closes #<n>` line outside code blocks and n is this issue, `issueAnswer` posts the comment it posts for a new pull request, with that pull request's URL, and leaves the issue open, in place of "The bot already proposed this repo". Verified by: tests of that case, and of an open bot pull request whose line names another issue, whose line sits in a fenced block, or which has two such lines, each getting the already-proposed answer.
- [ ] AC6: Each job of `add-plugin-issue.yml` and `report-issue.yml` sets `cache-mode: none` and passes issue numbers to commands only through `env:`. The `pick` job holds `contents: read`, `issues: read`, and `actions: read`; the read job adds `issues: read` to its present permissions; the `answer` job of `report-issue.yml` adds `actions: read`; the write job keeps its present ones. Verified by: `test/workflows.test.ts` for both files.
- [ ] AC7: README ("Proposing a plugin with an issue", "Reporting whether a plugin works"), CHANGELOG, and DESIGN state when each sweep runs, the conditions and limits of AC1, AC3, and AC4, and that an issue with any bot comment stays for a maintainer. They also state that a sweep run, even one with no issues, can cancel a pending `Discover plugins` run or issue run, and that a pending sweep can itself be canceled. The issue of such a canceled run is answered by a later sweep while it is under 7 days old, up to 3 issues a day, oldest first. A rerun of the write job answers each issue of its batch again. `pnpm test` and `pnpm check` pass.
